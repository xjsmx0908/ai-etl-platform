# 企业级 RAG 系统设计建议

> **Status:** Accepted
>
> **Accepted Date:** 2026-08-27
>
> **Review:** GitHub PR #1

## 文档目的

本文给出将当前 AI-ETL Platform 建设为完整企业级 RAG 系统时需要考虑的范围、架构原则和实施顺序。本文记录已通过评审的总体设计方向；具体实施范围仍须完成“待评估决策”后分阶段批准。

企业级 RAG 不只是“上传文档、生成向量、调用大模型”。系统必须同时闭环知识生命周期、访问控制、检索与答案质量、运行可靠性、审计合规和成本治理。

## 目标用户与使用场景

核心用户包括：

- **阅读者**：在授权知识空间内检索资料和提问。
- **知识贡献者**：上传、同步和维护业务文档。
- **空间管理员**：管理空间成员、文档版本、审核和发布。
- **租户管理员**：管理企业用户、权限、审计和恢复。
- **平台运维与 AI 工程师**：负责模型、索引、质量评测、容量和故障处理。

设计前应确认知识来源、数据敏感等级、文档与查询规模、更新时效、部署地域、合规要求和预算。还应定义可度量的 SLO，例如查询可用性、首 Token 延迟、文档可检索时延、RPO 和 RTO。

## 总体架构

```text
企业身份系统
     |
     v
Web / SDK / HTTP 入口
     |
     +-- 控制面：租户、用户、知识空间、权限、审批、审计
     |
     +-- 数据接入面：上传/同步 -> 扫描 -> 解析 -> 切块 -> 索引
     |
     +-- 查询面：授权 -> 混合检索 -> 重排 -> 生成 -> 校验 -> 引用
```

架构应优先形成以下深模块，让复杂规则隐藏在小而稳定的接口后面：

1. **Identity & Policy 模块**：统一处理租户、RBAC/ABAC、知识空间和文档权限。
2. **Knowledge Catalog 模块**：负责文档身份、版本、生命周期、发布状态、有效期和权威性。
3. **Ingestion 模块**：负责幂等接入、解析编排、重试、DLQ、进度和失败恢复。
4. **Indexing 模块**：维护 embedding、全文索引、索引版本和一致性检查。
5. **Retrieval 模块**：封装混合召回、过滤、融合、去重、重排和证据充分性判断。
6. **Answer 模块**：生成答案、绑定引用、验证忠实度并执行安全拒答。
7. **Evaluation 模块**：统一离线评测、回归门禁、在线反馈和版本对比。

模块是否物理拆分为独立进程，应由扩缩容、安全隔离和团队所有权决定，不能仅为了微服务化而拆分。

## 数据权威与一致性

| 数据 | 权威存储 | 设计要求 |
| --- | --- | --- |
| 原始文件 | 对象存储 | 不可变、版本化、校验哈希 |
| 文档状态与权限 | PostgreSQL | 唯一事实来源，事务更新 |
| 向量 | Qdrant | 派生数据，可重建 |
| 全文索引 | Elasticsearch | 派生数据，可重建 |
| 缓存 | Redis | 可丢失，不能承载业务真相 |
| 审计记录 | PostgreSQL 或 WORM 存储 | 追加写、可追溯、不可静默修改 |

向量库中的 metadata 只能用于检索下推，不能成为最终授权依据。查询必须先确定租户和知识空间，在检索时应用权限过滤，并在生成前通过 Knowledge Catalog 再次验证发布和生命周期状态。

跨 PostgreSQL、Kafka、Qdrant 和 Elasticsearch 的写入不能依赖普通顺序调用。建议采用 Transactional Outbox、幂等消费者、索引清单和定期对账，使消息丢失、重复消费或单索引写入失败都可以检测和恢复。

## 文档接入与治理流程

完整文档链路应包括：

1. 认证调用者，校验目标知识空间、写权限、文件类型和大小。
2. 执行病毒扫描、敏感信息检测、文件哈希和幂等检查。
3. 将原始文件写入对象存储，并在同一数据库事务中创建文档版本和 Outbox 事件。
4. 由 Outbox 发布 Kafka 任务；消费者按阶段记录处理进度。
5. 执行解析、OCR、版面和表格识别、文本规范化及结构化切块。
6. 记录页码、标题路径、来源、有效期、权限和模型版本等 metadata。
7. 使用明确版本的 embedding 模型生成向量，写入向量与全文索引。
8. 对比预期与实际 chunk 数，确认所有派生索引完整后标记 ETL 完成。
9. 默认空间可按政策自动发布；受管空间必须经过独立人员审核。
10. 更新产生新版本并使旧版本失效；删除需清理对象、索引、缓存和检索资格，同时保留必要审计。

完成 ETL 不等于文档已发布。任何未发布、已过期、已归档、被取代或索引不完整的文档都不能进入生产答案。

## 查询与答案流程

```text
认证
-> 解析租户、角色和知识空间
-> 查询分类或受控改写
-> Dense + BM25 混合召回
-> 权限、发布状态和有效期过滤
-> 融合、去重和可选重排
-> 证据充分性判断
-> LLM 生成
-> 引用绑定与忠实度验证
-> 返回有据答案或无来源拒答
```

查询设计应遵守以下规则：

- 知识空间必须在检索前解析，不能由搜索结果反向决定。
- 权限过滤必须下推到所有检索后端，并在生成前再次校验。
- 没有充分证据时返回统一拒答，不能依赖模型自行判断。
- 实际引用只包含真正支撑答案的 chunk，不能把所有召回结果当作引用。
- Prompt、模型、embedding、切块规则、索引和检索配置必须版本化。
- Query Rewrite、重排和跨文档规划只有在业务 Gold 数据上证明有效后才能启用。

## 安全与合规

企业部署至少需要考虑：

- OIDC/SAML 单点登录、SCIM 用户同步，以及 RBAC 与属性策略结合。
- 传输和静态加密、KMS、密钥轮换、私有网络和最小权限账号。
- 上传恶意文件、Prompt Injection、越权检索、敏感信息输出和模型供应商数据泄露。
- 管理操作、文档发布、权限变化和查询访问的不可抵赖审计。
- 数据驻留、保留期限、Legal Hold、用户数据删除和合规导出。
- 限流、配额、上传限制、租户资源隔离和异常行为告警。

生产环境不得直接暴露数据库、Kafka、Qdrant、Elasticsearch 或对象存储管理端口。

## 可靠性、可观测性与成本

所有异步阶段应支持幂等、超时、有限重试、指数退避、DLQ、背压和断点恢复。平台应提供索引重建、差异对账、文档重处理和级联删除工具，并定期执行备份恢复与故障切换演练。

统一 Trace ID 应贯穿入口、Kafka、解析、embedding、检索、重排和模型调用。关键指标包括：

- 上传成功率、处理时延、队列积压、重试和 DLQ 数量。
- 空切块率、解析失败率、索引数量差异和索引新鲜度。
- 查询 P50/P95/P99、首 Token 延迟、无答案率和超时率。
- Recall@K、MRR、引用正确率、忠实度、权限负例和拒答准确率。
- 每租户 Token、embedding、存储和模型成本。

## 质量评测与发布门禁

Mock 模型只能验证链路，不可作为检索质量证据。真实质量体系应包含：

1. 经业务负责人签署的领域 Gold 数据集。
2. 单文档、多文档、精确标识、时间有效性、冲突资料和无答案问题。
3. 跨租户、无权限、未发布、已删除和 Prompt Injection 等安全负例。
4. 解析、检索、重排、答案和引用分别计分，避免最终分数掩盖故障阶段。
5. 每次模型、Prompt、切块或索引变更均运行离线回归。
6. 通过影子流量、小比例灰度和可回滚配置验证线上效果。

发布门禁应同时覆盖质量、安全、延迟、可用性和成本，任何单项不达标都不能扩大流量。

## 实施顺序

建议按以下顺序推进：

1. 明确业务范围、数据分类、容量假设、SLO、RPO/RTO 和验收指标。
2. 建立业务 Gold 语料及审批责任，固化权限和知识生命周期规则。
3. 设计数据模型、模块接口、失败语义、威胁模型和数据流图。
4. 完成一个包含正常、无权限、更新、删除和故障恢复的端到端垂直链路。
5. 建立 Transactional Outbox、幂等处理、索引清单与自动对账。
6. 完成真实模型质量测试、容量测试、故障注入和备份恢复演练。
7. 接入企业身份系统，完成安全、隐私和合规评审。
8. 以受控租户试点，观察真实查询分布、失败模式、成本和用户反馈。
9. 只有质量、安全和 SLO 同时达标后，才逐步扩大生产流量。

## 当前项目的建议优先级

当前项目已经具备完整 RAG 工程链路、Knowledge Catalog、发布治理、评测和可观测基础。下一阶段建议依次完成：

1. 获得业务负责人签署的企业 Gold 数据集，形成正式质量验收基线。
2. 引入 Transactional Outbox 和索引清单，消除注册表、Kafka 与双索引间的一致性风险。
3. 将受管文档的双管理员发布流程纳入自动化 E2E。
4. 接入 OIDC/SAML 和 SCIM，替代仅适合本地或试点的账号体系。
5. 建立生产网络隔离、供应链安全、数据保留和集中合规能力。
6. 定义并验证 SLO、容量模型、备份恢复和跨故障域部署。
7. 根据真实业务评测决定是否启用 reranker、Query Rewrite 或跨文档规划。

现有 `internal/knowledgecatalog` 应继续作为权限与发布规则的核心 seam。规则应集中在该模块接口后，而不是散落到 HTTP 处理器、检索实现和前端逻辑中。

## 待评估决策

进入详细设计前，需要业务与技术负责人共同确认：

- 首批上线部门、知识空间和业务问题范围。
- 私有部署、企业云或托管模型的选择及数据出境约束。
- 用户规模、文档规模、更新频率、并发量和成本上限。
- 身份提供商、权限粒度、审批责任人与审计保留期限。
- 正式 SLO、RPO/RTO，以及可以接受的降级和拒答策略。
- Gold 数据集的所有者、签署流程和上线质量门槛。

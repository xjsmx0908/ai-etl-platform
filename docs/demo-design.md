# 企业级演示页面设计方案

> 目标：让面试官在 5-10 分钟内看懂项目架构、亲手验证核心能力、留下「工程化完备」的印象。
> 定位：不是「一个 RAG 聊天框」，而是「可交互展示企业级 RAG 工程能力的演示平台」。
> 状态：设计稿，待确认后实施。

## 1. 设计原则

1. **企业级 = 每个能力都有数据支撑，不是功能堆砌。**
   页面每个模块旁边都有对应指标（延迟、成本、token、Recall），证明「不只是能跑」。
2. **可主动验证，不是被动观看。**
   面试官可以自己问问题、看检索链路、测拒答、看成本——亲手验证比听你说有说服力。
3. **帮你说清系统为什么好。**
   页面展示的是「普通 RAG demo 没有的东西」：检索链路可视化、权限过滤、拒答防护、
   成本观测、质量评测、可运维性。
4. **一条故事线贯穿。**
   顶部引导 + 预设演示路径，避免面试官打开后不知道看什么。

## 2. 信息架构（5 个 Tab）

```
┌────────────────────────────────────────────────────────────┐
│  AI-ETL Platform  ·  企业文档知识问答平台                     │
│  [问答工作台] [检索质量] [系统可观测] [Agent编排] [数据接入]   │
└────────────────────────────────────────────────────────────┘
```

| Tab | 目标 | 面试官验证点 |
| --- | --- | --- |
| 问答工作台 | 核心交互，讲清「检索→生成」链路 | 流式回答、来源、缓存、成本、拒答 |
| 检索质量 | 用数据证明「检索是真的好」 | Recall 曲线、评测方法论、实验决策 |
| 系统可观测 | 证明「可运维、可监控」 | 服务健康、指标、告警、成本趋势 |
| Agent 编排 | 展示智能体能力 | Agent run 步骤、工具调用 |
| 数据接入 | 展示 ETL 能力 | 上传→处理流程、可靠性 |

## 3. Tab 1：问答工作台（核心）

### 3.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│  提问输入框  [快捷问题▾]  [上传文档▾]                         │
├──────────────────────────────┬──────────────────────────────┤
│  回答区（SSE 流式）            │  检索链路详情（折叠）          │
│  · 流式输出                   │  · 路由策略 exact/semantic/hybrid│
│  · 来源卡片（doc_id/内容/score）│  · 缓存命中 Y/N + 耗时        │
│  · 拒答提示（无证据时）         │  · 召回来源 + 分数条          │
│                              │  · 权限过滤提示                │
├──────────────────────────────┴──────────────────────────────┤
│  答案元信息栏：prompt版本 · token用量 · 估算成本 · 总耗时      │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 关键交互

- **快捷问题下拉**：预置 5-6 个种子数据能命中的问题（文件格式、上传大小、权限分级、
  缓存机制、检索排序、重试机制）。面试官一键提问，避免输入冷启动。
- **拒答演示按钮**：「问一个知识库外的问题」（预置），展示系统正确输出
  「未找到相关文档」——证明幻觉防护，这是企业 RAG 的核心差异点。
- **检索链路详情**：每次查询展开显示路由策略、缓存命中、多路召回、权限过滤。
  这是普通 RAG demo 完全没有的，最能体现工程深度。
- **来源卡片**：可点击展开完整 chunk 内容 + score，证明回答可追溯。

### 3.3 数据来源

- `/v1/query` 现有响应（answer/sources/token_usage/prompt_version）
- **需后端补充**：Response 加检索元信息（`retrieval.strategy`、`retrieval.cache_hit`、
  `retrieval.candidate_count`、`retrieval.permission_filtered`），目前这些只在
  trace span 里，未进响应。

## 4. Tab 2：检索质量

### 4.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│  语义集评测结果                                              │
│  · Recall@1 / @3 / @5 图表（真实模型）                        │
│  · pass_rate / 负样本拒答率                                  │
├─────────────────────────────────────────────────────────────┤
│  评测方法论（关键叙事）                                       │
│  · 锚点集 vs 语义集对比（说明为什么 100% 是假象）              │
│  · 抖动基线 4.26%（说明实验差异怎么判断）                      │
├─────────────────────────────────────────────────────────────┤
│  实验决策（数据支撑）                                         │
│  · hybrid 保留（ES 关 vs 开：52% vs 69%）                     │
│  · 英文 rerank 关闭（on vs off：69% vs 74%）                  │
└─────────────────────────────────────────────────────────────┘
```

### 4.2 面试官验证点

- 直观看到「检索质量是真的」——有真实 Recall 曲线，不是口头承诺
- 理解评测方法论：为什么锚点集的 100% 不可信，语义集才是真实水平
- 看到「用数据做工程决策」：hybrid 保留、rerank 关闭都是实验结论

### 4.3 数据来源

- `docs/evals/semantic-golden-set.json` + 最新评测报告（`docs/evals/reports/`）
- 建议前端加载一个静态 `docs/evals/reports/latest.json`，或在构建时嵌入

## 5. Tab 3：系统可观测

### 5.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│  服务健康（各容器状态）                                       │
│  query-api · etl-worker · parser · qdrant · es · redis ...  │
├──────────────┬──────────────┬──────────────┬────────────────┤
│ 查询延迟 p95  │  错误率       │  LLM 成本     │  token 总量     │
├──────────────┴──────────────┴──────────────┴────────────────┤
│  关键指标趋势（Prometheus 查询）                              │
│  · 请求量 · 延迟 · DLQ 增长 · ES dead letter                 │
├─────────────────────────────────────────────────────────────┤
│  告警状态（Active Alerts）                                   │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 面试官验证点

- 证明系统「可运维」：有完整指标、告警、追踪，不是玩具
- 实时看到成本增长（每问一个问题，成本数字跳一下）——企业最关心
- 服务健康一目了然（绿/黄/红）

### 5.3 数据来源

- 服务状态：query-api 新增 `/v1/system/health` 聚合各服务 healthz
- 指标：前端读 query-api 的 `/metrics`（Prometheus 格式）或经 Prometheus API
- 注意：Prometheus 端口 9090 公网不可达，需经 query-api 代理或后端聚合

## 6. Tab 4：Agent 编排

### 6.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│  任务输入框：让 Agent 完成「查询知识库中的 X」                 │
├─────────────────────────────────────────────────────────────┤
│  Agent Run 可视化（时间线）                                  │
│  · 步骤1: planner 决策 → rag_query 工具调用                   │
│  · 步骤2: 工具结果 → planner 决策 → final                    │
│  · 每步显示 thought / tool / 参数 / 结果 / 耗时               │
├─────────────────────────────────────────────────────────────┤
│  运行统计：状态 · 步数 · 工具分布                              │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 面试官验证点

- 展示 Agent 不只是聊天，而是「编排 + 工具调用」的工程
- 展示 durable run（状态持久化、可从任意步恢复）
- 展示工具注册、参数校验、权限（审批）

### 6.3 数据来源

- 现有 `/v1/agent/runs` + `/v1/agent/runs/{id}` API（已实现）
- 前端创建 run → 轮询状态 → 渲染步骤时间线

## 7. Tab 5：数据接入

### 7.1 布局

```
┌─────────────────────────────────────────────────────────────┐
│  上传区：拖拽/选择文件 → 立即上传                             │
├─────────────────────────────────────────────────────────────┤
│  处理流程可视化                                              │
│  · 上传 → Kafka 异步 → 解析 → 切块 → 向量化 → 入库            │
│  · 每步状态：排队中/处理中/完成/失败                          │
├─────────────────────────────────────────────────────────────┤
│  任务状态列表（doc_id · 状态 · chunk 数 · 耗时）              │
└─────────────────────────────────────────────────────────────┘
```

### 7.2 面试官验证点

- 现场上传一个文件，看异步处理全流程——证明 ETL 不是口头描述
- 展示幂等（重复上传复用结果）、失败重试（可故意用坏文件触发）

### 7.3 数据来源

- `/v1/upload`（现有）+ `/v1/agent/runs` 里的 `etl_task_status` 工具
- 或新增 `/v1/tasks/{doc_id}` 查询处理状态

## 8. 后端补充点（设计暴露的缺口）

| 补充 | 说明 | 优先级 |
| --- | --- | --- |
| `/v1/query` 响应加检索元信息 | strategy/cache_hit/candidate_count/权限过滤数（现只在 trace span） | P0 |
| `/v1/system/health` | 聚合各服务 healthz 状态 | P1 |
| `/v1/stats` 或经代理的 Prometheus | 前端获取指标/成本数据 | P1 |
| 任务状态查询端点 | `/v1/tasks/{doc_id}`（上传后查询处理状态） | P2 |

## 9. 实施步骤与优先级

### P0（核心，2-3 天）——Tab 1 问答工作台
- 后端：`/v1/query` 响应加检索元信息
- 前端：回答区 + 来源卡片 + 检索链路详情 + 成本/token 显示 + 快捷问题 + 拒答演示
- 目标：面试官打开就能验证「检索→生成」链路 + 幻觉防护 + 成本

### P1（1-2 天）——Tab 3 系统可观测 + Tab 2 检索质量
- 后端：`/v1/system/health` 聚合 + Prometheus 指标代理
- 前端：服务健康面板 + 指标卡片 + 成本趋势 + 评测数据可视化
- 目标：证明「可运维 + 质量有数据」

### P2（1-2 天）——Tab 4 Agent + Tab 5 数据接入
- Agent run 可视化 + 上传流程
- 目标：展示智能体 + ETL 能力

## 10. 演示脚本（面试官操作路径）

```
打开 http://<server>:3100
→ Tab1 点快捷问题「系统支持哪些格式的文件？」
   → 看流式回答 + 来源 + 检索链路（strategy/cache）+ 成本
→ 点「拒答演示」问知识库外问题
   → 看正确拒答（幻觉防护）
→ 连问几个问题，看成本/token 累计
→ Tab3 看服务健康 + 成本趋势（证明可运维）
→ Tab2 看 Recall 数据 + 实验决策（证明质量有据）
→ Tab4 让 Agent 执行任务，看编排
→ Tab5 上传一个文件，看处理流程
```

## 11. 技术风险与取舍

| 风险 | 应对 |
| --- | --- |
| Prometheus 9090 公网不可达 | 经 query-api 代理，或后端聚合指标 |
| SSE 经 Next route handler 已解决 | 已实现并验证 |
| 页面做太多反而臃肿 | 严格按 P0→P2 优先级，P0 先保证核心闭环 |
| 真实指标可能暴露「低 Recall」 | 这是**优势**——诚实数据 + 改进方向比虚假高分更有说服力 |

# 面试 Demo 演示脚本

> 地址：`http://170.106.202.186:3100`（面试官浏览器打开，免登录）
> 目标：10 分钟内带面试官亲手验证「企业级 RAG 的 5 个难点」都有解法。
> 顺序是设计过的：先讲检索（核心），再验证隔离与幻觉（安全），最后数据质量。

---

## 准备（面试前 5 分钟）

1. 确认页面能打开：`curl -s -o /dev/null -w '%{http_code}' http://170.106.202.186:3100/` → 200
2. 确认服务健康：浏览器打开页面 → 「系统可观测」Tab 应显示全部「up」
3. 清一遍语义缓存（避免命中旧结果影响展示）：
   ```bash
   docker exec ai-etl-platform-redis-cache-1 redis-cli --scan --pattern 'retrieval:*' | xargs -r docker exec ai-etl-platform-redis-cache-1 redis-cli DEL
   ```
4. 如遇异常先重启 query-api：`docker compose restart query-api`

---

## 演示流程

### 第 1 步 · 检索链路（2 分钟）——证明「不是简单 RAG」

**操作**：问答工作台 → 下拉快捷问题 → 选「一次最多能传多大的文件？」

**面试官看到**：
- 流式输出（一个字一个字出现）
- 引用来源（可展开看 chunk 内容 + score）
- 右侧「检索链路」：路由策略 = 混合检索、语义缓存 = 未命中、证据置信度 = 高 (0.75)

**你讲**：
> 这不是把问题直接丢给 LLM。先走检索：dense 向量 + BM25 关键词两路召回，RRF 按排名融合，
> 再按权限过滤。右侧能看到每次查询的路由策略、缓存命中、证据置信度。
> 再问一次同一问题 → 语义缓存命中 → 置信度面板显示「命中」，耗时下降。

**为什么值得看**：展示检索链路可视化——普通 RAG demo 完全没有，这是工程深度。

---

### 第 2 步 · 权限隔离（2 分钟）——证明「机密不泄露」

**操作**：点「权限演示」按钮（默认普通用户角色）→ 看到拒答；点右上角切「管理员」→ 再点「权限演示」。

**面试官看到**：
- 普通用户：蓝色提示「普通用户看不到这份机密文档」，拒答
- 管理员：返回机密来源（3 个），答案引用机密文档

**你讲**：
> 权限在检索源头过滤——机密文档对普通用户根本不会进入候选（Qdrant/ES 的 filter 在检索时生效），
> 不是回答后才检查。这是企业安全的核心：不是"回答了再删"，而是"根本搜不到"。

---

### 第 3 步 · 文档更新（1 分钟）——证明「数据是活的」

**操作**：数据接入 Tab → 填 doc_id（如 `contract-001`）→ 上传一份「付款期限 30 天」→ 回问答问「付款期限是几天」→ 答案 30 天 → 回数据接入换内容「付款期限 60 天」同 doc_id 重传 → 再问 → 答案变 60 天。

**你讲**：
> 企业文档会更新。同 doc_id 重传 = 替换旧版本（旧向量、全文索引、原始文件级联清理），
> 检索只返回新版本。demo 里改一次合同，答案就从 30 天变 60 天。

**为什么值得看**：这是企业级 RAG 和 demo 的分水岭——demo 永远只处理静态文档，企业文档是活的。

---

### 第 4 步 · 幻觉防护（1 分钟）——证明「宁可不答」

**操作**：点「拒答演示」按钮。

**面试官看到**：系统回答「未找到相关文档」，且有「幻觉防护演示」标注。

**你讲**：
> 问一个知识库里没有的问题，系统正确拒答而不是编造。检索链路面板显示证据置信度——
> 这是第二层防线：即使检索到内容，LLM 也要判断证据是否足够，不足就拒答。

---

### 第 5 步 · 质量有据（2 分钟）——证明「不是拍脑袋」

**操作**：切到「检索质量」Tab。

**面试官看到**：
- Recall@1 55% / @3 68% / @5 71%（bge-m3 真实模型，最近一次评测 2026-08-14 的柱状图）
- 三个实验决策卡片（ES 混合检索保留、英文 reranker 关闭、embedding 选型）

**你讲**：
> 锚点数据集的 100% 是假象（测的是关键词匹配）。换真实语义集后，先用 nomic-embed-text 测出
> Recall@1 只有 19%——然后换 bge-m3 大幅提升（最近一次真实评测 Recall@1 55%、@5 71%）。
> embedding 的语义分辨率是检索质量的决定性因素。每个配置决策都是对照实验用数据定的，差异都超过抖动基线。

---

### 第 6 步 · 成本可观测（可选，30 秒）

**操作**：问答 Tab 连问 2-3 个问题 → 切「系统可观测」看会话累计成本。

**你讲**：
> 每次查询的真实 token 和成本都记录。企业关心 ROI，成本可观测是底线。

## 面试官可能追问 & 应对

| 追问 | 应对 |
| --- | --- |
| 怎么从 19% 大幅提升？ | 评测暴露 nomic 的局限 → 换 bge-m3（中文优化）→ Recall@1 从 19% 显著提升（最近评测 55%、@5 71%）。embedding 选型决定检索上限 |
| 权限怎么保证的？ | 检索源头 filter（Qdrant/ES），不是回答后检查。演示了 user/admin 对比 |
| 文档更新怎么做的？ | doc_id upsert：重传 = 删旧（向量/全文/文件）再写新 |
| 怎么防止幻觉？ | 三层：权限过滤（机密不进候选）+ prompt 拒答契约 + 证据置信度可观测。硬阈值因分数分布重叠暂未启用（ADR 0006） |
| 这些数字哪来的？ | 真实模型（nomic-embed-text + deepseek-v4-flash）在 44 例语义集上实测，mock 只在 CI 用 |
| rerank 为什么关了？ | 实验：ms-marco（英文）对中文 0 例受益、2 例受害，69%→74%。exact pinning 仍独立工作 |

---

## 注意事项

1. **如实说数字来源**——页面显示最近一次真实评测（2026-08-14，bge-m3）Recall@1 55%、@5 71%，配合「从 nomic 19% 大幅提升」的改进过程讲才有说服力
2. **权限演示一定要先 user 后 admin**——顺序对了才直观
3. **文档更新演示不要用中文文件名**（doc_id 校验只允许字母数字 . _ -）
4. **如果命中语义缓存**，先清缓存再演示（见准备第 3 步）
5. **服务异常先重启 query-api**，再刷新页面
